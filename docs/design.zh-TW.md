# 設計說明

exifcard 背後的決策，以及形成這些決策的約束條件。[README](../README.zh-TW.md) 說明它做什麼與怎麼執行；本文件是給要修改程式碼、或要評估工程判斷的人看的。

本文件是 [design.md](design.md) 的繁體中文版，英文版為主要版本，兩者若有出入以英文版為準。

以下每一個數字都是實際量測的，不是估計；除非另有註明，量測對象是一張 33MP 的 Sony α7C II JPEG。

## 渲染流程

照片與資訊列從不重疊。這不是對設計的觀察，而是整個實作的支點：

```
Typst 只排資訊列                       Pillow 組裝卡片
┌──────────────────┐                   ┌──────────────────┐
│                  │                   │  照片位元組       │
│   （沒有照片）     │                   │  原封不動         │
├──────────────────┤                   ├──────────────────┤
│  7008 × 590      │  ───────────────> │  資訊列           │
└──────────────────┘                   └──────────────────┘
```

把整張卡片交給渲染器會比較簡單，代價是三件事，而且沒有一件是必要的：照片會被重新取樣、被轉換到渲染器的色彩空間、被壓成 8-bit。這不是假設：把一張 3000×2002 的 JPEG 以 1:1、完全不縮放地送進 Typst，22% 的像素會改變，最大差 5 階，並且耗時 1.4 秒；先前的無頭瀏覽器基於同樣的理由也是如此。把照片擋在外面，它的像素就能以離開相機時的樣子抵達輸出檔。

每個元素的位置都在 Python 裡以設計單位算好，然後才開始繪製。渲染器拿到的是絕對座標，只負責排字與光柵化。這一開始是被迫的——Typst 的 grid 儲存格是依內容決定尺寸，而不是依內部 box 上宣告的高度，這讓曝光讀數高了半個像素——但這個分工本身更好：`strip.measure` 與 `strip.render` 從此共用同一套算式，不可能各自漂移。

## 文字渲染

資訊列由 Typst 排版，而不是用 Pillow 繪製。為了排一條文字而背上一整套排版引擎是真實的成本，所以值得說清楚它換到了什麼。

設計稿在每一個文字元素上都指定了字距——曝光讀數 `.1em`、機身型號 `.04em`、鏡頭型號 `.03em`。而 **Pillow 沒有字距 API**。`ImageDraw.text` 的 `spacing` 參數是**行**與行之間的距離。要做出 `.1em`，就必須逐字繪製並自行推進筆點。

這麼做同時也放棄了字體自己的度量。以內建的 Archivo 在 100pt 下量測：

```
                        "AV" 整串      "A" + "V" 分開      差值
Typst                        130.20          133.00       2.80    ← 有套用 kerning
Pillow（基本排版）             138.00          138.00       0.00    ← 沒有
```

Archivo 帶有 GPOS 表。Pillow 的預設排版引擎會忽略它，而選用的 Raqm 引擎並不在標準 wheel 裡——本環境的 `HAVE_RAQM` 回報 false，會靜默退回基本排版。所以用繪圖庫實作，器材名稱會**既失去字體指定的 kerning**，又要在上面疊一層手工字距，而這張卡片的整個前提就是排版必須精確。

但也不需要一整個瀏覽器。Chromium 量同一組字得到 130.141 與 132.969，差值 2.828——同一張 GPOS 表、同一個 shaper，因為兩個引擎都用 HarfBuzz。在卡片實際會出現的字串上，兩者相差在 0.03 設計像素以內。

## 為什麼不用瀏覽器

資訊列原本由無頭 Chromium 渲染，直到數字不再支持這個選擇。

```
                        Chromium                     Typst
安裝           190MB 瀏覽器，需要             62MB，一般的 wheel
              另一個指令下載                  由 uv sync 裝好
一條資訊列      89ms                          5.4ms
一張 33MP 卡片  656ms                         463ms
```

安裝那一欄還低估了：`playwright install chromium` 會同時抓完整瀏覽器與 headless shell，約 530MB，而這個工具只會用到後者。

但決定性的因素既不是體積也不是速度。**瀏覽器的文字輸出與平台有關。** Blink 會把 ascent 與 descent 捨入到整數像素、對 half-leading 取下限、把行框量化到 1/64 像素，最後再把繪製的基線對齊到整數像素——而且各平台做得不完全一樣。這就是為什麼像素比對只能是本機檢查、CI 從來看不到，也是為什麼這個 repo 自己宣稱「任何機器都渲染一致」其實從未被驗證。

Typst 的輸出與平台無關，而 `tests/test_strip_golden.py` 就是用來守住這一點：四張參考圖在 macOS 錄製，以 `array_equal` 在 macOS、Linux 與 Windows 上比對。用容差的話，無論結論成立與否都會通過，所以這裡沒有容差。

瀏覽器有三個行為必須重現，每一個都是量出來而非假設出來的：

- **字距會加在每一個字元之後，包含最後一個**，所以帶字距的元素右緣會多出一格空白。Typst 只加在字元之間。同樣的短缺會在每一個字型 fallback 邊界重複一次，因為 Typst 會在涵蓋字型改變的地方開新的 shaping run——`α7C II` 是一個字串但兩個 run，α 來自 Noto Sans、其餘來自 Archivo，量出來正好少一格。
- **Typst 遇到溢出會換行，瀏覽器則是溢出。** 換行會靜默地把一行變成兩行，改變一個沒有任何紓解手段的高度，比看得見的溢出更糟。因此每個文字葉節點都被釘在自己量到的寬度上，只可能溢出。
- **Typst 沒有 opacity 屬性。** 內建的 SVG 標誌把透明度寫在根元素上，這正是瀏覽器對 `<img>` 設 `opacity` 的效果；點陣標誌則折進 alpha 通道，因為背後的紙是不透明的，合成結果相同。

Blink 的捨入則是**刻意不重現**。重現過，而且與 Chromium 吻合到 0.0000——但那正是平台綁定本身，把它帶進新的渲染器等於把限制一起帶過來。改用設計自己的數字，代價是卡片相對於瀏覽器在 macOS 上的輸出最多位移 0.875 設計像素：以卡片實際的放大倍率來說，是字緣上的幾個像素。

Typst 的版本是鎖死的，`typst==0.15.0`，不是下限。它還在 1.0 之前，小版本之間出現過破壞版面的改動，所以升級是一次完整重新驗證，不是例行更新。

## 無損合成

`--lossless` 呼叫外部的 `jpegtran` 而不是使用 Pillow，因為位元完全相同這件事本身就排除了「解碼」。任何走 Pillow 的路徑都會把檔案變成像素再編碼回去，而那個往返**本身就是損失**——沒有任何 quality 設定能避免，只能讓它變小。

要維持完全相同，就必須在不展開的前提下搬移已儲存的 DCT 係數。Pillow 沒有這樣的 API：它讀得到 JPEG 的量化表，但讀不到係數。純 Python 的替代方案是實際查證過的，不是憑印象：

```
jpeglib        1.0.2    wheels: 只有 cp38
jpegtran-cffi  0.5.2    wheels: 無，只有原始碼
```

所以 `jpegtran` 是誠實的相依。它維持選用，而且只有 `--lossless` 需要它。照片的長寬必須是 16 的倍數，因為那是 JPEG 的最小編碼單元（MCU）；做不到時這個旗標會直接報錯而不退回，因為一個會靜默降級的承諾比錯誤更糟。

但它確實靜默降級了很久，而且上面那些防護都沒擋到。`jpegtran -copy` 管的是**它正在編輯的那個檔案**——畫布——有哪些標記會留下，而不是被塞進去的照片。畫布寫出來時既沒有 EXIF 也沒有色彩描述檔，再加上 `-copy none`，於是 `--lossless` 交出一張兩者皆無的卡片：每個係數都位元精確，而 Display P3 或 Adobe RGB 的照片接著被當成 sRGB 讀，卡片的主體反而錯了。現在標記會寫進畫布並一起複製過去。

有一個差異留了下來，而且無法移除。解碼之後，卡片最後一列的照片像素與原圖不同——4288×2848 的畫面裡的 4288 個像素，就那一列，在接縫處。儲存的係數完全相同；改變的是底部邊緣的 chroma 上取樣現在下方有資訊列，而不是什麼都沒有。這是在區塊層級合成次取樣 JPEG 的性質，不是檔案裡的損失。

## 色彩

卡片會被標上照片的 ICC 描述檔，因為照片是主體、它的位元組不被碰。這使得照片的描述檔就是卡片的描述檔，其他所有東西都必須移進去。

資訊列不會自己到那裡。設計稿用十六進位表示顏色，那代表 sRGB，而渲染器輸出的就是那些數字、本身不帶描述檔——所以在廣色域來源上，它們被放在錯誤的空間裡解讀。把每個顏色經過卡片被標上的描述檔再轉回來量測：

```
                    Display P3    Adobe RGB (1998)
暖白紙                  0 階            1 階
機身墨色                1 階            6 階
日期灰                  1 階            4 階
```

差異很小，而理由值得說明：色盤是接近中性的灰與暖白，在任何色彩空間裡都很接近，而且設計規則禁止強調色。它只在這個前提成立時才小，而程式不該假設這個前提。現在資訊列會在兩者接合之前先被帶進卡片的描述檔；照片不會，因為它本來就在裡面。

## 編碼預設

JPEG 輸出預設為 quality 95，沿用來源的色度取樣，但**不**沿用它的量化表。卡片是拿來看的衍生作品，原檔仍留在圖庫裡。早期的版本沿用了來源 JPEG 的量化表——那是另一個問題（如何保存原檔）的正確答案——結果產出一張**比來源還大**的卡片：

```
                                       體積      佔來源     照片區偏差
來源（α7C II，4:2:2）                 18.76 MB      100%     —
沿用相機的量化表                       19.57 MB      104%     平均 0.12
quality 95 + 相機的色度取樣             6.87 MB       37%     平均 1.07
quality 95 + Pillow 預設的 4:2:0        6.35 MB       34%     平均 1.10
```

預設是第三列：quality 95，並沿用相機的色度取樣，所以拍成 4:2:2 的機身不會被悄悄砍成 4:2:0。平均偏差接近 255 階中的 1 階，在任何觀看尺度下都看不出來。

這個回歸之所以長期沒被抓到，是因為**每一個測試問的都是「圖看起來對不對」，而未壓縮的版本在那個標準下看起來更好**。現在有一個直接針對編碼本身的測試。

HEIC 的 quality 是映射到 x265 的參數，不是量化刻度，所以跨格式的數字不可比較——`heic 70` 大致落在 `jpg 95` 的保真度。HEIC 另外在約 28MP 以上必須分塊編碼，否則 libheif 會產生一個它自己解不開的檔案；分塊的體積代價約 1%。

## 字級與照片比例

縮放原本直接由卡片寬度推導，這對直幅照片是懲罰：直幅的長邊是高度，所以卡片比較窄，字就跟著縮小。一張 9:16 的手機直拍，字級只有橫幅的一半左右。

現在資訊列在自己的畫布上排版，畫布寬度為 `D`，再從那裡縮放：

```
a = 照片高 / 照片寬
D = clamp(604 / a, 450, 760)      # 畫布越窄，字越大
資訊列縮放 = 卡片寬 / D
```

| 比例 | D | 曝光讀數行（卡片等高時） |
|---|---|---|
| 3:2 | 760 | 14.2px |
| 1:1 | 604 | 12.6px |
| 4:5 | 483 | 13.9px |
| 2:3 | 450 | 11.8px |
| 9:16 | 450 | 10.1px |

橫幅落在 760，輸出逐像素不變；有一個測試以參考圖釘住這件事。2:3 與 9:16 觸及下限——450 是資訊列本身塞得下的最窄寬度——所以達不到橫幅的字級，但已經是塞得下的最大值。

長機身名配上長鏡頭名可能讓那一列溢出。卡片不換行、不截斷、也不縮寫，而是分兩級讓步：

1. **收緊**——曝光讀數的字距（`.1em` → `.04em`）與左右兩組之間的欄距（`20` → `12`）。約多出 8–10% 的寬度，而且完全不損失字級。
2. **撐開畫布**——只有在收緊仍不夠時才做，整塊等比縮小。

兩種寬度都是在瀏覽器裡以實際文字量測的，逐張照片、每次從乾淨狀態開始——單向的棘輪會讓某張卡片因為前一張照片的鏡頭名很長而被縮小。

這也是為什麼顯示名稱對照表不是用來縮短名稱的。它們把內部代號換成產品的正式名稱（`ILCE-7CM2` → `α7C II`）；判斷一個名稱裡哪些字比較重要，不是工具該做的決定。

撐開刻意不設上限。設了上限，畫布就會在某個寬度停住，而超出的文字會在那個寬度上重新壓到簽名上——同一種失敗，換一條路徑抵達。超過 900 時改由執行訊息說明，並指出哪一筆對照表項目能讓卡片回到原本的字級。

## 地點說明能要求什麼

兩段讓步屬於器材名。它不延伸到地點說明，而這個差別不是風格問題：

| | 器材名 | 地點說明 |
|---|---|---|
| 來源 | EXIF | 使用者自己打的 |
| 長度 | 受限於產品實際叫什麼 | 無上限 |
| 可否改短 | 只能靠對照表，而那會改動相簿裡**每一張**用到該鏡頭的卡片 | 改一行就好 |
| 完整呈現的義務 | 辨識——短到認不出是哪支鏡頭就沒有意義 | 沒有；設計本來就允許不顯示地點 |

所以畫布只由照片比例與器材名決定，量測時會先把地點拿掉。地點接著只能用簽名旁邊剩下的空間。它可以用第一段的收緊（不損失字級），不能用第二段。如果地點能撐開畫布，就等於讓一行使用者一秒就能改短的文字，把這張卡片的字級設得比相簿裡其他卡片都小，而卡片上沒有任何地方說明原因。

塞不下時該張照片失敗，並報出實際幾何量：

```
IMG_4821.HEIC  the location does not fit: it needs 334 design px of the 282 left
               beside the signature (canvas 450); shorten it in locations.toml
```

報幾何量而不是字數上限，因為根本不存在穩定的字數上限：80 個 `i`、80 個漢字、80 個大寫字母是三種不同的寬度，而日期還跟它們共用同一行。

預算（設計像素）：

| 卡片 | 整行可用 | 扣掉 `YYYY.MM.DD · ` 前綴後 |
|---|---|---|
| 3:2 橫幅、有簽名 | 592 | 510 |
| 3:2 橫幅、無簽名 | 720 | 638 |
| 9:16 直幅、有簽名 | 282 | 200 |

最後一列就是這條規則的代價：`Fushimi Inari, Kyoto` 量起來是 208，對上那一欄的 282，所以還能再加一個短詞，但加不了第二個。以直拍為主的相簿，這會是常態而不是例外——之所以接受，是因為那一行是卡片上唯一能讓作者無代價改短的東西。

## 焦距

卡片上的焦距是 **35mm 等效焦距**，不是鏡頭上刻的實體焦距。依序三步：

1. 相機有記錄 `FocalLengthIn35mmFilm` 就用它。
2. 沒有就用 `FocalLength`，也就是實體焦距。
3. 兩者都沒有就整項不顯示。零在這兩步都視同缺值：部分機身會寫 0 而不是省略標籤，那是同一件事，而且沒有任何鏡頭是 0mm。

實體焦距是鏡頭上刻的數字，這是採用它的理由，但它記錄不了實際的取景。在一台 iPhone 16 Pro 上量測：

```
                    FocalLength   FocalLengthIn35mmFilm
IMG_4350.heic         6.765mm             48mm
IMG_4355.JPG          6.765mm             30mm
```

兩種不同的取景，同一個數字。改變的是感光元件的裁切，而只有等效值帶得動這個資訊。任何裁切片幅的機身都有同樣的問題，只是沒這麼極端：X-E5 在 17mm 的取景等同於 26mm。

較舊的 DSLR——Canon EOS 700D、Nikon D90——根本沒有寫這個標籤，那些卡片就維持實體值。這使得一整批照片裡同時存在兩種基準，而卡片上沒有說明是哪一種；替代方案被否決了：替等效值加上標記，會讓符號只出現在現代機身上、舊機身沒有，反而把一個多數人不在意的區別放大。而且退回實體值正是卡片一直以來顯示的東西，所以沒有任何一張照片會比原本更差。

## 簽名

簽名在兩個軸上都有上限：寬度不超過 `signature_width`，高度不超過它所在的那一列，以先受限的為準。圖片周圍的透明邊界會在繪製前裁掉。

原本只用寬度決定尺寸，高度就完全交給檔案的長寬比。第二列高 35 設計單位、內容靠底對齊，所以比 108/35（約 3:1）更方正的簽名會渲染得比它的列還高，並往上穿過列間距撞進曝光讀數。資訊列高度是固定的，沒有任何東西會讓位，兩者就直接重疊。一個 2:1 的簽名會算出 52.6 單位高、對上 35 單位的列，結果就畫在 ISO 讀數上。

裁切是同一個道理。被縮放的是整張圖片，所以墨跡只佔檔案高度 56% 的簽名，實際只有要求尺寸的 56%，而且浮在基線上方而不是落在上面。「檔案要裁切到墨跡邊界」這件事原本只寫在設定檔的註解裡，沒有任何地方檢查。

## CJK 地點

不內建任何 CJK 字型。堪用的最小檔案是 9 到 17MB，對比卡片自己三款字型合計 2.8MB；多數使用者用不到，而倉庫是放這種二進位檔最糟的地方：git 歷史是永久的、字型無法 delta 壓縮，將來每更新一次版本就再疊一份完整副本。改成由使用者在 `config.toml` 登記自己已經有的檔案，依登記順序排在內建字型之後。

順序交給使用者，是因為靠語言判斷只能是猜測：`京都` 在中文與日文是同樣的兩個碼位，而兩邊有若干字的寫法不同。程式不會去檢查文字內容來挑字型。它做的是另一件事——當一行地點是由不只一個檔案畫出來時把這件事說出來，因為那正是同一行內字形設計開始不一致的時刻。

登記的字型排在字型堆疊的**最後**。堆疊是逐字解析的，而每一款 CJK 字型也都涵蓋拉丁字母，所以只要排在前面，它就會接管器材名與曝光讀數，把整張卡片的字體換掉且不會有任何訊息。

### 字級補償

漢字的墨跡比同一行的數字高，所以在相同 font-size 下地名會壓過日期——對整張卡片最安靜的那一行來說方向剛好相反。以字面外框而非字型宣告的 ascent 量測，因為眼睛對齊的是墨跡：

```
                              基線以上墨跡        對齊數字所需
JetBrains Mono 數字               0.741 em        —
Noto Sans TC                      0.842           0.880
Noto Sans JP                      0.832           0.891
Noto Sans KR                      0.832           0.891
Noto Sans SC                      0.842           0.880
Noto Sans CJK TC                  0.848           0.874
```

橫跨無襯線、襯線與圓體、四個語系變體，對齊所需的比例落在 0.874 到 0.891，所以 `CJK_SIZE_RATIO` 是單一常數 0.88，而不是一張要逐字型維護的表。它**必須**與字型無關：既然什麼都不內建，這個值就不可能針對某個特定檔案調校。

補償是按 CJK 字元的連續段落套用，而不是整行，因為地點常常是混排的——`京都 Fushimi Inari`——把整個元素縮小會連拉丁字母一起縮。

字距在每一段都重新指定，即使它本來就會繼承。繼承而來的 `letter-spacing` 帶著它在父元素上已經算出的長度：9px 行上的 `.1em` 繼承為 0.9px，進到 7.92px 的段落裡仍然是 0.9px。用 em 重新指定，才把字級與字距都綁回該段落自身的大小，這也是每個字的前進量能精確等於 `size × 0.88 × 1.1`、讓地點預算是算術而非量測的原因。

row 2 的高度不變。它的 35 設計 px 在扣掉鏡頭行與間距後留給日期行 11.0；未補償的 line box 是 10.8，補償後是 9.5，而比行盒小的行內子元素不會把它撐大。那 0.2px 的餘裕由 `tests/test_cjk.py` 釘住，因為這裡溢出是往上撞進 row 1，不是往下溢到紙上。

### 字型載入失敗

宣告了但檔案不存在的 face，並不會阻止 `document.fonts.ready` resolve。頁面接著會用系統提供的任何字型排版，被當成設計本身量測，再以同樣的狀態被截圖。cmap 檢查也抓不到：它讀的是使用者指定的檔案，不是瀏覽器實際拿到的東西。所以每一個頁面在量測或截圖之前都會檢查 `FontFace.status`，失敗就直接報錯，不產出卡片。

## 內建素材

字體與品牌標誌打包在套件內，所以卡片在任何機器上都渲染出相同結果，工具也能離線運作。全部都是自由授權：字體採用 SIL Open Font License，品牌標誌屬於公有領域的 `PD-textlogo`，每一個標誌的來源都記錄在 `logos.toml` 裡。

執行期才抓取標誌的做法評估過並否決了。那等於拿一個**根本不存在的**著作權問題（純文字字標未達原創性門檻），去交換網路相依、速率限制、不可重現的輸出，以及由資料庫而非人眼挑選的標誌。Wikidata 的 logo 屬性給 Leica 的是圓形紅點標、給 Sony 的是集團標；對一張以高度對齊標誌的卡片來說，兩者都是錯的。

一個標誌只有在 11px 的暖白紙上仍然站得住時才會被收錄。Nothing 的標誌是黑底白字，在那個尺寸下讀起來就是一條黑槓，所以它使用文字 fallback。

## 已知限制

- **每通道 8 bit。** 合成在 8-bit RGB 下進行，所以 10-bit 的 HEIF 進來時會被降精度。執行時會明確告知，而不是靜默降級。16-bit 管線可行，但需要為各格式分別實作編碼路徑。
- **不支援 RAW。** 卡片是在工作流程的末端製作的——照片已經挑選並調色完成，檔案本來就是 JPEG 或 HEIF。讀 RAW 會把工具拉進「顯影」這個職責，而那件事已經有別的軟體在做。
- **HEIC 超過約 28MP 需要分塊**，這是自動套用的。沒有分塊時 libheif 會寫出一個它自己讀不回來的檔案。
- **`--lossless` 需要 PATH 上有 `jpegtran`**，而 Windows 沒有標準的安裝套件。這個旗標會明確說明原因而不是莫名失敗；其餘功能在 Windows 上都正常。
- **沒有任何可用字型涵蓋的字元會畫成空框。** 系統字型永遠不會被使用，那正是卡片可重現的原因，所以沒有東西可以退而求其次。執行時會在渲染前先說出是哪些字元。
